Fork build of Kirin Tool for Linux 2.4.19 (downstream of Redminote11tech/kirin-tool-linux).

One-line: batch B+ of the 2026-11 warning cleanup — the four windows that hand-rolled
`INotifyPropertyChanged` no longer shadow `AvaloniaObject.PropertyChanged`; behaviour, bindings and
every device command are unchanged, and a new headless assertion proves the notification path still
reaches the rendered control.

Why the plan changed
- `docs/warnings-policy.md` originally said "use `AvaloniaObject.RaisePropertyChanged`". Avalonia
  11.3 has **no string overload** of `RaisePropertyChanged` — every overload takes an
  `AvaloniaProperty`. Bindings to plain CLR properties (`{Binding CurrentOperationText}` and friends)
  therefore *must* go through `INotifyPropertyChanged`; converting ~20 properties on `MainWindow` into
  `DirectProperty`/`StyledProperty` would have been a real binding-semantics change, not a warning cleanup.
- The actual smell was the mechanism batch A used to silence CS0108: `public new event
  PropertyChangedEventHandler? PropertyChanged` shadowed `AvaloniaObject`'s typed
  `PropertyChanged` (`AvaloniaPropertyChangedEventArgs`), so `x.PropertyChanged` meant two different
  things depending on the static type.

What changed (4 files, no behaviour change)
- `MainWindow`, `ProcessDialogUapp`, `PartitionSelectorDialog`, `FastbootPartitionSelector` now
  implement the interface member explicitly:
  `event PropertyChangedEventHandler? INotifyPropertyChanged.PropertyChanged` over a private field, and
  `OnPropertyChanged(string)` raises through that field. Same property names, same timing, same
  interface — which is exactly how the binding engine subscribed before (the classes already
  re-declared `INotifyPropertyChanged`, so interface dispatch was already going to the derived event).
  `x.PropertyChanged` now unambiguously means Avalonia's typed event again.
- `!`/suppression: none added; the compiler is as clean as it was in 2.4.18.

Verification
- `tests/UsbUpdateUi` (headless Avalonia) now asserts the *rendered* `TextBlock` re-renders after a CLR
  property change, not just that the property value changed. The assertion is sensitive: with the
  notification temporarily disabled the suite fails with
  "Bound status text did not re-render after the property change (INPC path broken)".
- `tests/suites.txt`: 25/25 exit 0 locally and in CI; `tests/StableParity` needed the two frozen
  boundary hashes refreshed (`MainWindow.axaml.cs`, `UI/ProcessDialogUapp.axaml.cs`) with a
  "behaviour unchanged" note, then passed.
- Warning budget unchanged: 0 CS/CA tree-wide, gate from `Directory.Build.props` still armed.

Known gaps
- The variant that would drop INPC entirely (CLR properties → `DirectProperty`) is deliberately not
  done: it changes binding resolution for every `{Binding}` on those windows and buys no warning.
  If it ever happens it needs its own branch, the whole headless GUI suite and a visual-parity pass.
