Fork build of Kirin Tool for Linux 2.4.18 (downstream of Redminote11tech/kirin-tool-linux).

One-line: the nullable-reference cleanup (batch B) is finished — the compiler now reports **zero**
CS/CA warnings on the app project (a local build only prints the three Avalonia XAML AVLN3001
notices that CI never sees), and every cleared code is now gated so it cannot come back.

Where this started
- 2.4.17 (batch A) took the log of run 43443391616 from 130 unique warning sites to 81. What was left
  was a single category: `<Nullable>enable</Nullable>` was switched on after most of the code existed,
  so CS8618/CS8625/CS8600/CS8603/CS8604/CS8620 fired on long-standing assumptions — mostly on the
  flashing hot paths.

Batch B (this release) — 76 unique sites, 160 raw compiler lines
- **Signatures widened instead of `!`-suppressed.** `FastbootClient` (`executablePath`, progress),
  `ProcessRunner` (`op`, progress, the shared `StringBuilder`), `OemInfoService`, `SuperMerger` and
  `FirmwareUnlocker` (interaction handler, options) now say which arguments are actually optional.
- **Flashing payloads are nullable end-to-end.** `UsbDownloadService` connection/port lookups,
  `USBUpdateFlasherService` partition callbacks and the first-super-header path, the
  `ProcessDialogUapp`/`FlashPartitionItem` source labels, and `OpLog.Begin` / approval argv lists
  (`IReadOnlyList<string?>?`) — every downstream consumer already filtered nulls, so behaviour is
  identical, but the type no longer lies about it.
- **Models and fields.** POCOs (`PartitionInfo`, `ProcessResult`, `FullOtaFile`,
  `ProgressItemViewModel`, `UnlockResult.Message`, …) get defaults where construction always assigned
  first; `VcomFlasher._serialPort` and `FastbootPartition.DumpPath` became honestly nullable, which is
  what their read sites already assumed.
- **One real defect fixed on the way:** `FlashFailureDescription` called `Split` on a captured fastboot
  output that can be null (a spawn failure produces no text), i.e. a null dereference while composing a
  failure message. It now falls through to the generic "see the fastboot log" text.
- `!` appears 23 times in the diff, once per genuine compiler-invisible invariant (constructor-order
  init, `TryGetUsbDevice` returning true, a payload behind a success gate), each with a comment. No
  `#pragma warning disable` was added anywhere.
- No wire command, byte, timing or retry changed. `tests/StableParity/boundary.json` hashes were
  refreshed for the nine frozen device-semantics files, each with a "behaviour unchanged" note.

Gate
- `Kirin-Tool.csproj` now gates the nullable set as well:
  `CS4014;CS0168;CA2022;CA1416;CS8600;CS8602;CS8603;CS8604;CS8612;CS8618;CS8620;CS8622;CS8625`.
  Gating a half-cleared category teaches people to sprinkle `!`, so this waited until the count was
  zero; from here a new nullable mistake fails the build instead of quietly joining a pile.
- Measured locally (`dotnet build Kirin-Tool.csproj -c Release --no-incremental`): 0 CS/CA warnings,
  AVLN3001 ×3 (runtime-loader notice for the three code-constructed dialogs; CI does not report it).

Verification
- `tests/suites.txt`: 25/25 harnesses exit 0 (hardware probes `VcomOpenProbe`/`UsbUpdateProbe` are
  excluded there by design — no device was contacted for this release).
- No new CLI/MCP surface, no GUI behaviour change, so no on-device smoke test was needed.

Known gaps (unchanged from 2.4.17)
- Batch B+ is still open: four `AvaloniaObject` subclasses keep a hand-written
  `public new event PropertyChangedEventHandler? PropertyChanged` instead of using
  `RaisePropertyChanged`. That is a refactor, tracked in `docs/warnings-policy.md`, not a warning left
  behind.
- The AppImage container remains `ubuntu:20.04` on purpose (glibc 2.31 floor, see
  `docs/portable-appimage.md`); only the CI runner images are pinned to `ubuntu-24.04`.
