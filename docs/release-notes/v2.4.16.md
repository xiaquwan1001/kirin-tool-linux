Fork build of Kirin Tool for Linux 2.4.16 (downstream of Redminote11tech/kirin-tool-linux).

One-line: v2.4.13, v2.4.14 and v2.4.15 all reported themselves as 2.4.13. They now report the
version they actually are.

What was wrong
- `Kirin-Tool.csproj` pinned `<FileVersion>2.4.13.0</FileVersion>` and
  `<InformationalVersion>2.4.13</InformationalVersion>` next to `<Version>`. Every later release
  bumped only `<Version>`, so `doctor` and `info --json` printed `2.4.13+<commit>` while the
  packages were 2.4.14/2.4.15. Anyone checking “am I on the build with the approval gate?” got the
  wrong answer.
- Found by the 2.4.15 real-device smoke test (`doctor` on the ELS-AN00), not by a unit test — which
  is why it survived three releases.

What changed
- The pins are gone: `Version` is the single source of truth and both assemblies derive
  `FileVersion`/`InformationalVersion` from it. The CLI project is bumped with it.
- New harness `tests/VersionMetadata` (7 checks) fails if anyone re-pins the metadata, if the two
  project files disagree, or if the built assembly's reported version differs from the csproj.
  It joins `tests/suites.txt`, so both CI pipelines run it.

Verified on the device
- `kirin-tool-cli doctor` on the ELS-AN00 (retail 4.2, adb up) now prints `2.4.16+4cdfd09…`.
- Read-only smoke on the same run: `capabilities`, `udev`, `logs list --json` (906 entries: 247
  sessions + 659 legacy files), `vcom-unlock --cpu hisi990 --dry-run` (plan-only, exit 4),
  `info --json`; `partitions` correctly reports “no fastboot device detected” while the phone is in
  adb mode.

Known gaps (unchanged from 2.4.15)
- MCP writes need a running GUI for the out-of-band approval.
- A whole-package USB Update still has no CLI/MCP face (debt D-12).
