Fork build of Kirin Tool for Linux 2.4.14 (downstream of Redminote11tech/kirin-tool-linux).

This release unifies the three surfaces. Every capability is now declared once, reachable from the
GUI, the CLI and MCP, executed through one service method, and admitted through one approval gate.
Nothing that can write to a device is GUI-only any more, and every operation leaves a replayable log.

Surface parity (new)
- Services/Capabilities/CapabilityRegistry.cs is the single source of truth: 22 capabilities, each
  naming its CLI command, MCP tool, GUI handler, write kind, parameters and declared side effects.
- tests/SurfaceParity enforces it in CI, in both directions: a capability whose command/tool/handler
  is missing fails, and a command, MCP tool or GUI handler that exists without a registry row also
  fails. The gate also refuses a GUI handler that is neither registered nor listed with a written
  reason in `tests/SurfaceParity/gui-ui-only.txt` (17 pure-UI handlers today). Run
  `dotnet run --project tests/SurfaceParity` for the exact check count on your tree — the count moves
  with every registry row, so it is not quoted here.
- Coverage in this release: 22 capabilities, 21 CLI commands, 21 MCP tools, and 18 capabilities with
  all three faces (GUI + CLI + MCP). The remaining four — `doctor`, `getvar`, `capabilities`,
  `backup` — are read-only CLI + MCP without a GUI handler, which the registry allows. No *registered*
  capability is GUI-only any more (6 were).
- Four read-only capabilities that existed only in the GUI gained CLI + MCP faces: partitions,
  psid, capabilities, udev.

Approval gate (new)
- Services/Approval adds one gate in front of every write: GUI modal prompt (per-item argv and side
  effects), CLI --yes (plus --allow-redline and a typed confirmation phrase for redline or
  irreversible work), MCP confirm:true followed by an out-of-band human approval through the GUI;
  if no GUI is running the call is refused with approval_required_human.
- Write tickets: DeviceWriteOps methods take a WriteTicket as their first argument, and only the
  gate can mint one, so a new write path cannot bypass approval by accident.
- The six former GUI-only writes are now three-surface: reboot, reboot-usb-update, write-sn,
  frp-remove, unlock-bootloader, usb-testpoint.

VCOM loader injection (real execution)
- vcom-unlock is no longer plan-only. CLI and MCP drive the very same
  FirmwareUnlocker.UnlockFastboot + VcomFlasher the GUI button uses: same frame layout, same
  CpuAddresses table, same loader order, no second protocol implementation.
- --stage-only all|null|xloader|rest for the vendor replug choreography, --port, --loader-dir,
  --ack-mode strict|lenient|off, --ack-timeout, --replug skip|prompt|wait:<s>, --use-fastflash-loader.
- One audit file per VCOM session (~/.local/state/kirin-tool/vcom-<UTC>-<cpu>.log, mode 600) shared
  by GUI and CLI: every frame, address, sequence, ACK byte or timeout, every prompt and its answer,
  and the final verdict. The GUI keeps the path on screen after the dialog closes.

Honest verdicts
- ACK accounting is part of the result: verified, reason, ack.missing, ack.missingRatio,
  stages[].framesSent, stages[].missing. A silent device yields
  conclusion=loaders-uploaded-unverified; the GUI shows an amber “Uploaded - Unverified” instead of a
  green success. --require-ack turns an unverified upload into a failure (exit 3).
- Loader preflight before the first frame: a missing or undecryptable loader fails with
  MissingLoader and framesSent=0; the old “Skipped, continue anyway” path is gone.
- --require-backup now fails when the backup cannot be created (exit 4) instead of silently
  continuing; --no-backup writes an audit line.
- Unknown CLI options are an error (exit 1); --lenient-args restores the old behaviour with a warning.
- In the GUI, the serial-number rewrite is verified by reading nve:SN back; only an identical
  read-back is reported as success, everything else says “Write Not Confirmed” with the value the
  device kept. The CLI/MCP `write-sn` path still reports on the fastboot exit code alone — tracked as
  an open item in [../debt-register.md](../debt-register.md) (D-03).

Operation logging
- Services/Diagnostics/OperationLogger writes one JSONL file per operation
  ($KIRIN_LOG_DIR/{vcom,fastboot,flash}/...): timestamp, pid, op, phase, tool, redacted argv, exit
  code, duration, stdout/stderr tails, ok and verdictSource (the exact reason the verdict was taken).
- The fastboot write path no longer starts processes outside ProcessRunner; the hardcoded
  oem unlock UUUUUUUUUUUUUUUU became a validated parameter (16 characters, checked before anything is
  sent to the device).

Testing
- 22 hardware-free suites (was 17) run by both CI pipelines from tests/suites.txt: the new
  SurfaceParity, ApprovalGate, OpLogging, VcomUnlockCli (pty fake BootROM) and VerdictHonesty
  harnesses join the existing set. StableParity still pins the wire behaviour: the VcomFlasher hash
  is unchanged in this release.
- Audits behind this batch: docs/audit-gui-blackbox.md (36 black-box GUI actions) and
  docs/audit-hardcoded-and-hidden-steps.md (95 hardcoded values, 43 silent degradations, 21 false
  successes, 27 platform assumptions). **Which of them this release actually closed, and which are
  still open, is recorded with per-item evidence in [../debt-register.md](../debt-register.md).**

Known gaps
- **The GUI's OEMInfo “Convert” button still writes the device directly** (`oeminfoerase-disablewp` +
  `oeminfowrite-KTModel@`/`KTVendor@`) while the registry declares `oeminfo` as plan-only: no CLI/MCP
  face, no approval gate. This is the top open item (D-01) in
  [../debt-register.md](../debt-register.md); “0 GUI-only writes” above holds for *registered*
  capabilities only.
- USB Update flashing still has no CLI/MCP face, and its success verdict still tolerates a failed
  handshake, skipped partitions and a short read (D-04/D-12 in the same file).
- MCP writes need a running GUI for the out-of-band approval; headless servers get a clear refusal
  rather than an implied consent.
- --ack-mode still defaults to lenient (the historical GUI behaviour), so an upload can be
  unverified but exit 0 unless --require-ack is passed.
- The VCOM session log and the generic operation log are written separately; merging them into one
  file per session is planned. **Fixed in v2.4.15** — since v2.4.15 the logs are merged: one operation =
  one session directory = one `session.jsonl` (docs/log-merge.md).
