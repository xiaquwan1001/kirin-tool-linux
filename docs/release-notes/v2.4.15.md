Fork build of Kirin Tool for Linux 2.4.15 (downstream of Redminote11tech/kirin-tool-linux).

Two themes: the logs a device operation leaves behind are now one replayable session, and the
remaining false-success paths are gone. Both were found by the previous release's own audit, not
by guessing.

Operation log: one operation = one session
- `sessions/<timestamp>-<pid>-<op>/` holds `session.jsonl` (the timeline), an optional
  `vcom-trace.txt` (human-readable) and `summary.json` (final verdict). VCOM frames, approval
  decisions and fastboot commands interleave in one file, with `sessionId`, `seq`, `parentId`,
  `capabilityId` and `approvalId` tying them together.
- New read-only `logs list | show <session|latest> | path` (CLI + MCP, no confirm needed):
  `logs list` answers “what did this tool do on this machine”, `logs show` replays one session.
- Legacy `{vcom,fastboot,flash}/*.jsonl` and `vcom-*.log` stay readable and are marked
  `legacy: true`.
- Every remaining write path is inside the log now: `flash.xml`, `flash.ota`, `flash.rescue`,
  `flash.image`, `backup.preop`, `backup.dump`, `usbupdate.{flash,unpack,dload-cleanup}`,
  `oeminfo.{read,convert,write}`, `downgrade.erase`. Steps carry `ok:` / `failed:` / `degraded:` /
  `skipped:` prefixes, so a degradation can no longer look like a success.

ACK policy per entry point
- `vcom-unlock --ack-mode` now defaults to `strict` for CLI and MCP: a silent device fails with
  exit 3, `verified=false`, `failureKind=device-rejected` and the ACK counters as evidence.
- The GUI keeps `lenient` (the historical behaviour): it reads the answer but reports an amber
  “Uploaded - Unverified” instead of a green success.
- `--ack-mode lenient` still exits 0 by design, but the result carries `verified=false` and
  `reason=ack_missing:<n>`. `--require-ack` turns any unverified upload into a failure.

Write verdicts taken from the device
- `WriteReport` (Applied / Partial / Failed / Unconfirmed) replaces the unconditional
  `applied: true, gate: "applied", exitCode: 0` in every write command's JSON. A device refusal is
  `applied: false, gate: "failed"` with the reason.
- CLI `write-sn` now reads `nve:SN` back and compares, exactly like the GUI: only an identical
  read-back exits 0; otherwise “Write Not Confirmed” with the value the device kept.
- OEMINFO is split into `oeminfo-convert` (host-side image, plan-only) and `oeminfo-flash`
  (redline, irreversible, typed confirmation) because the GUI used to write it directly with no
  approval gate at all.
- Same treatment for the downgrade path: `downgrade-enable` stays a plan, the actual
  `oem oeminfoerase-*ver` erase is `downgrade-erase` — redline, irreversible, typed confirmation,
  one shared `DeviceWriteOps` entry, CLI and MCP faces included.
- USB Update transfers now return a three-state verdict: `verified` (every required partition
  answered on a handshaken link), `partial`, `failed`. A missed handshake, a missing `.img`/
  `.img.header`, a 0-byte image or a stream that ended early are explicit `degraded:`/`skipped:`/
  `missing:` events instead of silent `continue`s that still reported success. Protocol bytes,
  timing, retries and block size are unchanged.

Testing and guards
- 24 hardware-free suites (was 22) in `tests/suites.txt`; new `LogMerge` and `UsbUpdateVerdict`
  harnesses, `OpLogging` grew to 127 checks, `ApprovalGate` to 88, `WriteGates` to 70.
- `SurfaceParity` now runs 413 checks over 25 capabilities, 24 CLI commands, 24 MCP tools,
  35 GUI handlers: 25 have all three faces, 0 writable capability is GUI-only, and every write
  must declare its approval kind, its shared service method and its GUI gate call.
- Mutation-checked in this release: breaking a CLI command name, adding an unregistered GUI
  handler, and clearing a write capability's `Approval` each turn the gate red.

Debt register
- `docs/debt-register.md` tracks every audit item as `fixed-in-2.4.15` / `open` / `wontfix` with
  evidence. D-01, D-02, D-03, D-04 and D-13 are fixed in this release; the remaining open items are
  listed there with the reason they are not fixed yet.

Known gaps
- MCP writes still need a running GUI for the out-of-band approval; a headless server is refused
  with `approval_required_human` rather than implied consent.
- A whole-package USB Update still has no CLI/MCP face (debt D-12), so the three-state verdict is
  reachable from the GUI and from `usb-testpoint` only.
- Session logs are partitioned per process; concurrent instances write separate sessions by design.
